# Repository instructions

Follow the repository `.editorconfig`, analyzers, formatters, and CI checks. Do not manually override deterministic formatting rules. Before completing code changes, run the relevant configured validation for the files you changed.

The following style rules require developer judgment and are not duplicated in deterministic tooling:

4. Ініціалізатори простих або анонімних об’єктів із **1–2 властивостями** можна залишати в одному рядку. Для **3 і більше** — кожна властивість на окремому рядку.
5. У ланцюжках викликів кожен наступний виклик розміщувати на окремому рядку: `.AsNoTracking()`, `.SingleOrDefaultAsync()` тощо.
6. У складених умовах із **3 і більше перевірками** кожну перевірку розміщувати на окремому рядку. Короткі умови з двома перевірками можна залишати в одному рядку.
7. Переносити довгі сигнатури методів і довгі списки аргументів. Якщо список перенесено — кожен параметр або аргумент розміщувати на окремому рядку.
8. Не розривати короткий складений тип на частини: наприклад, `Func<BackgroundJob, DateTimeOffset, Task<bool>>` залишати разом.
9. Ставити порожній рядок перед `if`, якщо перед ним виконувалися інші інструкції.
10. Відділяти групу присвоєнь або ініціалізацій порожнім рядком від наступної групи викликів методів.
11. Не вставляти порожні рядки між послідовними викликами методів, які належать до однієї логічної групи.
12. Відділяти перевірки вхідних даних від основної роботи методу порожнім рядком.
13. У багаторядковому методі відділяти фінальний `return` від попередніх дій порожнім рядком. Якщо `return` — єдина інструкція в блоці, додатковий рядок не потрібен.
16. Не змінювати логіку, порядок інструкцій, назви чи текст коментарів під час форматування.
17. виклики валідації та компактні декларації конфігурації БД записувати горизонтально, незалежно від кількості аргументів. Якщо рядок надто довгий — переносити після коми, залишаючи кілька аргументів у рядку, де це зручно. Не застосовувати автоматично принцип «один аргумент — один рядок».
